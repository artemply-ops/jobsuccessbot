# JobPilot: архитектура, логика решений и стыковка с сервисом подготовки к собеседованиям

Обновлено 25.11.2026. Документ для команды (или сессии Claude) соседнего проекта, который продолжает путь кандидата
после отклика: этапы собеседований, подготовка, разбор. Цель: понять, что JobPilot уже знает о кандидате и вакансии,
какие правила нельзя нарушать и как связать два сервиса без двойного ввода данных.

Подробности по коду: `docs/ARCHITECTURE.md` (где что менять), `docs/ECONOMICS.md` (цены и маржа),
`docs/BACKLOG.md` (блокеры, развилки, техдолг).

## 1. Что делает JobPilot и где граница

Один сценарий (JTBD с пивота 08.11.2026): **«сделать резюме под конкретную вакансию»**.

```
Материалы кандидата ─► Профиль ─► Вакансия ─► 2-3 уточнения ─► Пакет документов ─► Одна итерация правок
(файл, текст, голос)  (обезл.)   (текст или  (по пробелам      (резюме, одностраничник,
                                  ссылка)     покрытия)         письмо, сообщение менеджеру,
                                                                LinkedIn; PDF и Word)
```

Есть второй, быстрый путь: «резюме из опыта» без вакансии (письма и сообщения менеджеру в нём нет).

**Граница ответственности.** JobPilot заканчивается на готовом пакете для отклика. Всё, что после отклика
(статус по вакансии, этапы интервью, подготовка к вопросам, тестовые задания, разбор после встречи, оффер),
в JobPilot не реализовано и логично уходит в соседний проект.

Код поиска вакансий и каталога компаний (блок 2 MVP) сохранён, но скрыт флагом `SEARCH_ENABLED=false` (развилка Р4).

## 2. Каналы и общая схема

```
Telegram-бот (aiogram 3) ──┐
Mini App (PWA в Telegram)  ┼── services/* ── PostgreSQL (прод) / SQLite (локально)
Сайт и PWA в браузере ─────┘       │
                                   ├── llm.structured ── OpenRouter (только обезличенный текст, JSON-схема)
                                   ├── billing (гранты, лимиты, списания)
                                   ├── payments (ЮKassa на сайте, Stars в Telegram)
                                   └── notify / push (бот + Web Push)
```

| Слой | Технологии |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy async, Alembic |
| Фронт | Vite + React 19 + TypeScript, одна сборка для сайта, PWA и Mini App, раздаётся бэкендом |
| ИИ | OpenRouter, OpenAI-совместимый API, ответ строго по JSON-схеме. Модели в `.env`: `LLM_MODEL_MAIN` (Sonnet 5.5), `LLM_MODEL_SCORING` (Haiku 5.5), `LLM_MODEL_VISION` |
| Голос | Yandex SpeechKit (РФ), пока заглушка: ключа нет |
| Документы | `fpdf2` (PDF, свои шрифты, превью PNG), DOCX; OCR сканов: Tesseract локально + vision-модель по обезличенному изображению |
| Хостинг | Timeweb, Москва, общий сервер 4 ГБ RAM; Docker Compose (db, app, caddy); HTTPS через Caddy; домен job-pilot.ru |

**Главный принцип:** правила живут в `backend/app/services/`, каналы тонкие. Бот, сайт и Mini App вызывают одни
и те же функции, поэтому правка правила сразу действует везде. Соседнему проекту стоит повторить этот принцип.

Один процесс `app` = API + PWA + бот + планировщик (`RUN_BOT_IN_API=true`, `RUN_SCHEDULER=true`).
Фоновые задачи: asyncio в процессе и таблица `jobs` (очередь Arq + Redis отложена, развилка Р7).

## 3. Данные: что JobPilot знает о кандидате и вакансии

Ключевой для стыковки факт: **все смысловые данные хранятся обезличенными**, контакты отдельно.

| Сущность (таблица) | Что внутри | Полезно для собеседований |
|---|---|---|
| `users` | id кабинета, tg_id, гость или нет, `tone` (нейтрально / на вы / на ты), `source` | Единый идентификатор, стиль общения |
| `identities` | Привязанные способы входа: почта (в нижнем регистре), Яндекс ID | Склейка кабинетов |
| `contacts` | ФИО, почта, телефон, город, ссылки, фото, `vault` (маркер → значение) | **Не передавать.** Единственное место ПДн |
| `sources` | Сырые материалы: файлы, текст, голос. Содержат ПДн | **Не передавать** |
| `profiles` | `ProfileData`, версии. Обезличен | Да: опыт, навыки, достижения с фактами, ожидания, ценности, стоп-факторы, стиль письма |
| `targets` | Вакансия кандидата: `parsed` (`VacancyParsed`), уточняющие вопросы, `coverage` до генерации | Да: требования, обязанности, ключевые слова, грейд |
| `vacancies` | Карточка вакансии (компания, название, город, зарплата, url) | Да |
| `dossiers` | Досье компании (`DossierData`): сфера, миссия, ценности, продукты, сигналы культуры, tone of voice, источники | Да: основа подготовки к «почему наша компания» |
| `packages` | Готовые документы: `cv` (JSON), письмо, сообщение менеджеру, LinkedIn, `fact_flags`, `coverage` после, версия | Да: что именно кандидат отправил работодателю |
| `grants`, `billing_usage`, `payments` | Тарифы, лимиты, оплаты | Только если общий биллинг |
| `llm_usage` | Токены и стоимость по шагам, без текстов | Учёт себестоимости |

### Схемы, которые стоит переиспользовать (`backend/app/schemas.py`)

- `ProfileData`: headline, summary, target_roles, seniority, skills[{name, level, years}], experience[{company, role,
  period, achievements[{text}]}], industries, education, languages, expectations{salary_min, cities, formats,
  relocation}, values, stop_factors, writing_style.
- `VacancyParsed`: title, company_name, company_site, city, remote, salary, seniority, responsibilities,
  requirements, nice_to_have, keywords, language.
- `DossierData`: business_area, summary, mission, values, products, culture_signals, tone_of_voice, sources.
- `CV`: headline, summary, highlights[{value, label}], skills, experience[{company, role, period, bullets}].
- `FactCheck.flags[]`: text, where, reason, severity.

### Покрытие требований (`services/coverage.py`): самый ценный мост к собеседованиям

По каждому требованию вакансии хранится:

```json
{"requirement": "опыт управления командой от 5 человек",
 "status": "covered | partial | missing",
 "evidence": "где в тексте подтверждено",
 "in_profile": true,
 "question": "вопрос кандидату, если подтверждения нет"}
```

Плюс `keywords_covered`, `keywords_missing`, итоговый `score` 0-100. Замер делается дважды: по исходному профилю
(`targets.coverage`) и по готовому резюме (`packages.coverage`).

Для подготовки к интервью это готовый список рисков: требования со статусом `partial` и `missing` почти наверняка
всплывут на собеседовании, а `evidence` по `covered` подсказывает, какие истории кандидату рассказывать.

## 4. Логика ключевых решений (почему так)

Формат: решение, причина, отвергнутая альтернатива. Даты по `PROJECT_MEMORY.md`.

| # | Решение | Почему | Что отвергли |
|---|---|---|---|
| 1 | Зарубежная LLM + обязательное обезличивание до отправки (28.09) | Качество текстов выше, ПДн не покидают периметр: ФИО, контакты, имена третьих лиц заменяются маркерами, реальные значения подставляются только при выгрузке (`export.py`) | Российская LLM без обезличивания: слабее на генерации |
| 2 | Любой вызов ИИ только через `llm.structured` со страховкой `has_pii` | Одна точка контроля: если в тексте остался телефон или почта, запрос не уходит (`PIILeakError`) | Вызовы модели из разных мест кода |
| 3 | Ответ модели строго по JSON-схеме (Pydantic) | Предсказуемая структура, проверка кодом, без разбора свободного текста | Свободный текст и парсинг регулярками |
| 4 | Контакты в отдельной таблице `contacts`, в профиле их нет | Профиль можно показывать модели и другим сервисам без риска | Контакты внутри профиля |
| 5 | Проверка фактов (`SYSTEM_FACTCHECK`) обязательна для каждого пакета | В резюме нельзя выдуманных фактов. Неподтверждённые пункты резюме выкидываются автоматически, неподтверждённое в письме блокирует выгрузку до подтверждения кандидатом | Доверять генерации |
| 6 | Недостающее не додумываем, а спрашиваем (2-3 уточнения по покрытию) | Правило всего сервиса: ответ кандидата пишется в профиль как новый источник | Модель «дописывает» опыт под требования |
| 7 | OpenRouter вместо прямого API Claude (16.10) | Смена модели без правки кода; API напрямую недоступен с российских IP | Прямой API провайдера |
| 8 | Трафик к OpenRouter и Telegram через прокси (socks5h, выход DE) | OpenRouter с российского IP отвечает 403 | Без прокси |
| 9 | Голос только Yandex SpeechKit (РФ) | Голос это ПДн | Зарубежное распознавание |
| 10 | Источники вакансий только легальные, hh.ru не парсим, robots.txt соблюдаем | Анонимный API hh.ru отвечает 403, парсинг сайта запрещён; кандидат вставляет текст вакансии сам | Парсинг hh.ru |
| 11 | Контакты рекрутеров из вакансий не храним | Чужие ПДн без основания | Сохранять для «написать рекрутеру» |
| 12 | Vite SPA вместо Next.js (28.09) | Одна сборка раздаётся самим FastAPI, один деплой, Mini App не нужен SSR | Next.js с отдельным сервером |
| 13 | Один кабинет на бот, Mini App и сайт (15.11) | Учётка = `users.id`, способы входа привязываются; при объединении ничего не удаляется | Отдельные учётки по каналам |
| 14 | Гость работает без входа, вход нужен перед сборкой документов | Ниже порог входа, ПДн собираются только после согласия | Регистрация на первом экране |
| 15 | Биллинг через «гранты» (лимиты со сроком или без) | Бесплатный старт, разовая покупка, тариф и промокод это одна сущность; новый продукт добавляется строкой в `PRODUCTS` без миграции | Отдельные таблицы под каждый тип оплаты |
| 16 | Списание только в `tailor.build`, в одной транзакции со сборкой | Если сборка упала, списание откатывается, деньги не теряются | Списание до генерации |
| 17 | Внутри Telegram цифровые товары только за Stars | Правила Telegram; на сайте ЮKassa | ЮKassa в боте |
| 18 | Эмбеддинги в MVP не используем (28.09) | Лексический предфильтр + оценка моделью дешевле и проще на 4 ГБ RAM | Векторная БД |
| 19 | Режим без ИИ: шаги отвечают заглушкой и ведут дальше | Сервис работает и тестируется без ключа; после подключения пересчёт | Падать без ключа |
| 20 | Фронтенд собирается локально, на сервере никогда; базовый образ по хэшу зависимостей | Инцидент 16.10.2026: `npm ci` на сервере исчерпал память, лёг соседний бот | Сборка на сервере |
| 21 | Учёт токенов `llm.track(user_id, action)` без текстов запросов | Себестоимость по действию и пользователю, без хранения содержимого | Логи с промптами |

## 5. Варианты стыковки с проектом «собеседования»

Внешнего API для сторонних сервисов, OAuth-провайдера и исходящих вебхуков в JobPilot **сейчас нет**. Ниже варианты
от простого к глубокому; выбор за владельцем.

### Вариант A. Передача контекста по ссылке (минимум, 1-2 дня работы)

После сборки пакета JobPilot показывает кнопку «Готовиться к собеседованию». Она создаёт одноразовый токен
(механизм уже есть: `login_tokens`, срок короткий) и ведёт в соседний сервис. Тот одним запросом забирает
**обезличенный** пакет контекста (схема ниже) и дальше живёт сам.

- Плюсы: сервисы независимы, ПДн не передаются, нет общей базы.
- Минусы: изменения в профиле после передачи не синхронизируются.

### Вариант B. Общий кабинет (средний, неделя и больше)

Соседний сервис доверяет JWT JobPilot (`Authorization: Bearer`, HS256, `sub` = `users.id`) или получает свой
способ входа в таблице `identities`. Данные читаются через API JobPilot: `GET /api/profile`, `GET /api/targets`,
`GET /api/targets/{id}`, `GET /api/packages`, `GET /api/packages/{id}`.

- Плюсы: один вход, один тариф, всегда свежие данные.
- Минусы: общий секрет JWT или отдельный сервис-токен, связанные релизы, нужен контракт версий API.

### Вариант C. Новый модуль внутри JobPilot

Этапы интервью как ещё один `services/interview.py` на тех же таблицах, каналах и биллинге.

- Плюсы: ноль интеграции, переиспользуется всё (бот, Mini App, оплата, обезличивание, фактчек).
- Минусы: растёт один процесс на общем сервере 4 ГБ (см. Р7), продукты не развиваются раздельно.

### Предлагаемый пакет контекста для передачи (вариант A, черновик, не реализован)

```json
{
  "schema": "jobpilot.handoff/v1",
  "user_ref": "непрозрачный id, не tg_id и не почта",
  "tone": "neutral | vy | ty",
  "profile": "ProfileData, обезличенный",
  "vacancy": "VacancyParsed + company_name, url",
  "dossier": "DossierData или null",
  "coverage": {"before": "отчёт по профилю", "after": "отчёт по готовому резюме"},
  "package": {"cv": "CV", "cover_letter": "текст", "recruiter_message": "текст", "version": 2},
  "fact_flags": "оставшиеся флаги, если были",
  "created_at": "ISO 8601"
}
```

Маркеры вида `[CANDIDATE]` в текстах остаются маркерами. Реальные имя и контакты соседний сервис запрашивает
у кандидата сам, со своим согласием на обработку.

### Что соседний сервис может построить из этих данных

| Данные JobPilot | Этап собеседования |
|---|---|
| `coverage` со статусами `partial` и `missing` | Список «опасных» вопросов и ответы без выдумок |
| `coverage.evidence` + `experience.achievements` | Истории в формате STAR по требованиям вакансии |
| `dossier` (миссия, ценности, продукты, tone of voice) | «Почему мы», вопросы к работодателю, стиль ответов |
| `vacancy.responsibilities` и `seniority` | Кейс-интервью, тестовое, вопросы по грейду |
| `expectations` + ориентир по зарплате (`GET /api/targets/{id}/salary`, данные «Работы России») | Подготовка к разговору о деньгах |
| `package.cv` и письмо | Что кандидат уже заявил: ответы на интервью должны с этим совпадать |
| `tone` | Тон подсказок |

## 6. Правила, которые соседний проект должен соблюдать, если берёт данные JobPilot

1. ПДн и контакты не передаются и не запрашиваются у JobPilot. Только обезличенные `profile`, `vacancy`, `dossier`,
   `package`.
2. Во внешнюю LLM уходит только обезличенный текст, с проверкой на остаточные ПДн перед отправкой.
3. Голос, если будет, распознаётся в РФ.
4. Хранение данных пользователей из РФ на серверах в РФ; уведомление в РКН (у JobPilot пока не подано, блокер Б4).
5. Никаких выдуманных фактов в ответах-заготовках для интервью: опираться на `profile` и ответы кандидата,
   неподтверждённое помечать.
6. Контакты интервьюеров и рекрутеров без основания не хранить.
7. Секреты (ключи, токены, строки подключения) только в `.env` на сервере, в переписку не попадают.

## 7. Текущее состояние JobPilot (25.11.2026)

- Прод: коммит be6bf50 (выкачен 24.11.2026), `pytest` 98 passed; сайт job-pilot.ru и www, бот @job_success_bot.
- Работает: профиль из файлов и текста (OCR сканов), вакансия текстом или ссылкой, уточнения, покрытие требований,
  досье и цвета компании, пакет из 5 документов с фактчеком, PDF и Word, правки, балл до и после, ориентир
  по зарплате, один кабинет, вход по почте, Web Push, админка с расходами и воронкой, ежедневные резервные копии.
- Не работает или не включено: оплата на сайте (нет магазина ЮKassa, Б2), оплата в Telegram (решение по Stars, Б3),
  голос (нет ключа SpeechKit, Р6), вход через Яндекс ID (нет ключей, П8), поиск вакансий (скрыт, Р4).
- Юридическое: уведомление в РКН (Б4), проверка оферты, политики ПДн и слогана юристом (Б5).
- Технические риски: фоновые задачи в процессе app (Т1), копии базы на том же сервере (Т15), один прокси
  до OpenRouter (Т6), себестоимость правки не замерена (Т7, Т16), нет e2e-тестов интерфейса (Т8).

## 8. Вопросы к владельцу перед стыковкой

1. Какой вариант стыковки: A (ссылка с контекстом), B (общий кабинет) или C (модуль внутри JobPilot)?
2. Общий биллинг или раздельные тарифы?
3. Где живёт соседний сервис: тот же сервер (память на пределе) или отдельный?
4. Нужна ли обратная связь: статус отклика и этапы интервью возвращаются в кабинет JobPilot?
5. Кто оператор ПДн во втором сервисе: тот же ИП или другое лицо (влияет на согласие и уведомление в РКН)?
