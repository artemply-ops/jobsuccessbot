# Архитектура JobPilot

Обновлено 15.11.2026. Главный принцип: **правила живут в `services/`, каналы тонкие.** Бот, PWA, Mini App и сайт
вызывают одни и те же функции сервисов, поэтому правка правила сразу действует во всех каналах.

## Каналы

```
Telegram-бот (aiogram) ──┐
Mini App (PWA в Telegram) ┼── services/* ── БД (Postgres на сервере, SQLite локально)
PWA и сайт в браузере ───┘        │
                                  ├── llm.structured (OpenRouter, только обезличенный текст)
                                  ├── billing (лимиты, списания, промокоды)
                                  └── payments (ЮKassa на сайте, Stars в Telegram)
```

- **Сайт и PWA** это одна сборка `web/`. Без входа показывается лендинг с ценами, после входа приложение.
- **Mini App** та же сборка внутри Telegram: вход по initData, оплата через Stars (`openInvoice`).
- **Бот**: `bot/handlers.py` (старт, файлы, голос), `bot/cv_flow.py` (сценарий резюме), `bot/billing_flow.py`
  (тариф, промокод, оплата Stars).

## Где менять что

| Что меняем | Где |
|---|---|
| Цены, лимиты тарифов, бесплатный старт | `services/billing.py`: `PRODUCTS`, `FREE` |
| Что считается платным действием | `services/billing.py`: `ACTIONS`; списание в `services/tailor.build` |
| Тексты оплаты в боте | `bot/billing_flow.py` |
| Экран оплаты в PWA | `web/src/pages/Billing.tsx` |
| Лендинг и юридические страницы | `web/src/pages/Landing.tsx`, `web/src/pages/Legal.tsx` |
| Модель для шага | `.env`: `LLM_MODEL_MAIN`, `LLM_MODEL_SCORING`, `LLM_MODEL_VISION` |
| Домен | `.env`: `DOMAIN` (Caddy, можно несколько через запятую) и `PUBLIC_URL` |

## Биллинг

Одна сущность на все случаи: **грант** (`grants`) это набор лимитов `{package: N, revision: M}` со сроком или без.

- бесплатный старт: грант `free` без срока, создаётся при первой проверке;
- разовая покупка: грант без срока;
- тариф на неделю или месяц: грант со сроком;
- промокод: грант любого продукта из каталога.

Каждое списание это строка `billing_usage` со ссылкой на грант. Остаток = лимит гранта − списания по нему.
Сначала тратится грант с ближайшим сроком, бессрочные в конце. Новый продукт или акция добавляются строкой
в `PRODUCTS`, без миграций.

Порядок в коде: канал заранее вызывает `billing.require` и показывает оплату, если лимита нет. `tailor.build`
снова вызывает `require` до модели и `consume` после успешной сборки. Если сборка упала, транзакция
откатывается вместе со списанием, и деньги не теряются.

## Оплата

- `payments` это одна строка на попытку оплаты: провайдер, продукт, сумма, статус.
- **ЮKassa** (сайт и PWA в браузере): `POST /api/billing/checkout` возвращает ссылку на оплату.
  Вебхук `POST /api/billing/yookassa/webhook` не доверяет телу запроса: статус перепроверяется запросом в API ЮKassa.
- **Stars** (бот и Mini App): счёт в XTR. Payload счёта это id платежа. Грант выдаётся
  в обработчике `successful_payment`.
- Выдача гранта идемпотентна: повторный вебхук или повторное событие ничего не начисляет.

## Учёт токенов

`llm.structured` просит у OpenRouter usage и пишет в `llm_usage` только числа: модель, шаг (имя схемы), токены,
стоимость, пользователя и действие (`llm.track`). Текст запросов не сохраняется.
Сводка: `GET /api/admin/usage?days=N`.

## Ограничения, о которых помнить

- Миграций (Alembic) нет: `init_db` создаёт новые таблицы и досоздаёт nullable-колонки. Переименование или
  удаление колонки потребует Alembic.
- Бот работает в процессе API (`RUN_BOT_IN_API=true`): оплата Stars и вебхук ЮKassa обрабатываются в одном процессе.
- Вход на сайт сейчас только через Telegram Login Widget (нужен `/setdomain` у BotFather). Вход по почте это
  следующий шаг: появится таблица способов входа, а `users.tg_id` уже nullable.
